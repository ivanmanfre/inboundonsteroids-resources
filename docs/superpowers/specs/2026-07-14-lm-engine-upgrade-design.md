# Lead-Magnet Engine Upgrade — Design

**Date:** 2026-07-14
**Status:** Design (awaiting review → per-phase implementation plans)
**Repo:** `~/Desktop/resources` (static GitHub Pages LM host) + n8n LM generator pipeline

## Goal

Make every lead magnet dramatically better as a technical artifact, at the **engine** level, so improvements apply to Ivan's LMs *and* every client's LMs (multi-tenant leverage: ship once in `_engine/`, lift all tenants). This is a platform upgrade, not a one-off resource design.

## Grounding: current architecture

Live LMs at resources.inboundonsteroids.com are a **static GitHub Pages site** rendered by hand-written **vanilla-JS engines**:

- One `_engine/<format>.{js,css}` per format: `assessment.js` (×27 live), `calculator.js` (×5), `guide.js` (×12), `checklist.js` (×8), plus others.
- Content injected as a per-slug `data.json`; a thin `<slug>/index.html` wrapper loads `/_engine/<format>.js` + `./data.json`.
- Per-prospect **brand restyle** at view time via URL query params (`?accent=&font=&bg=&logo=&hero=`) read by the engine (`assessment.js:198-226`). Built by `personal-site` `lib/assessmentEmbed.ts`.
- Covers via Gemini (Railway `scroll-recorder` `/lm-cover-gemini`).
- View/capture beacons → Supabase edge fn `lm-beacon` → `lm_events` / `assessment_results`.
- `_engine/shared.js` loads on all 57 engine LMs (shared injection point).
- `_engine/assessment-v2.js` exists (~51KB, richer engine) but **0 live LMs use it**; sole consumer ever is `_engine/demo/assessment-v2/`.

Content is generated by the n8n **Lead Magnets** workflow (Claude via Railway proxy → JSON spec → `<slug>/data.json`), triggered by ClickUp status transitions; re-render via `POST /webhook/regen-lm`; index/sitemap via `POST /webhook/publish-library`.

## Decisions (locked in brainstorming)

- **Roadmap decomposed into 4 phases**, dependency-ordered `2 → 3 → 5 → 4`. Each phase is independently shippable and reversible. Implementation plans are written **per phase**, not as one giant plan.
- **Phase 1 (scrollytelling) is PARKED** — weakest multi-tenant bet: the generator can't author it, so it stays per-LM hand work until a later generator-schema round. Fold into a future generator upgrade.
- **`viz.js` = hand-built brandable primitives**, not an Observable Plot / charting-library wrapper. Total anti-slop control, near-zero payload, renders in any tenant's brand via existing tokens.
- **v2 keeps the email capture gate**, made configurable via a `data.json` flag (default on) — the gated actionable output is the value exchange.

## Cross-cutting principle: truth under "operating record"

The brand is "operating record, not opinion." The single deciding risk across the roadmap is **LLM-fabricated numbers rendered as authoritative computed outputs** (incident class already hit: fabricated-numeral blind QA, 2026-06-23). The invariant, enforced in Phase 2 and preserved in Phase 5:

> The generator emits **formulas and inputs only, never result numerals.** All displayed numbers are computed **deterministically** by the engine from the viewer's actual answers. No LLM-emitted value ever reaches a page. Personalized/threaded params fill inputs and prose slots only — never formula source.

## Phase 2 — v2 engine safe, generator-authorable, gated for truth

**The foundation. Everything else depends on it.**

### What ships
1. **Compat shim.** `normalizeAnswer` (`assessment-v2.js`) returns `null` for untyped questions → legacy `data.json` renders "0/100". Add a fallback branch treating an untyped question as legacy scored-choice (`answers[index].score / max_score`, mirroring `assessment.js:59-76`). Result: v2 renders all 27 existing LMs at parity.
2. **Port the color brand-mirror into v2 (non-regression).** v2 dropped the scan-embed / query-param restyle system that `assessment.js:196-390` has. That is live functionality (scan embeds, client boards depend on it). Port the `?accent=&font=&bg=&logo=` reader + embed-mode (`.lmc-embed`, CTA suppression) into v2. Phase 5 later extends this same mechanism from color to data.
3. **Configurable capture gate.** Restore the legacy email gate in v2 behind a `data.json` flag (default on).
4. **Teach the n8n generator the v2 schema.** Emit `type` per question (`number` / `multi_select` / `short_text` / `likert`), `normalize_formula`, `scoring_formula`, `overall_scoring_formula`, and `computed_outputs[]` with `format` (`currency_per_period`, `hours_per_period`, …). This is the multiplier: every future client LM gets computed outputs with no per-LM work.

### The validation gate (deciding risk, built in — not bolted on)
- **Formulas-not-values contract**, enforced: generator output schema forbids result numerals; only formulas + inputs are allowed in the compute path. Engine computes via `safeEval` from viewer answers (already v2's design).
- **Render-QA step in the pipeline:** each generated `data.json` is run through the engine headless with synthetic answer sets; assert every computed output is finite, in-range, and sane. **Fail → LM does not publish, routes to error** (same pattern as post-gen lint).

### Data flow
n8n generate (formulas + inputs, no result values) → render-QA validation node → publish `data.json` → engine computes at view time from viewer answers.

### Error handling
- Validation fails → block publish, route to error status.
- First-time taker, no history → v2 already degrades cleanly (Supabase RPCs `phase_d_lm_assessment_*` deployed 2026-05-17, return empty rowsets cleanly; history features stay invisible, nothing throws).

### Why safe to ship
v2 is **additive** — a separate engine file. Legacy LMs keep pointing at `assessment.js` until a specific one is explicitly flipped. Nothing live changes on merge.

### Testing
- All 27 legacy `data.json` render **non-zero** under v2 (parity vs legacy score).
- A generated v2 LM passes schema validation + render-QA.
- Brand-mirror parity: embed with query params, restyle matches legacy.
- Gate on/off via flag.

### Notes / caveats
- Confirm the v2 anon key is a valid publishable key (`sb_publishable_...`, NOT dead `iat=1738702127`).

## Phase 3 — `viz.js`: one brandable chart module for every LM

### The problem
Every chart is hand-rolled one-off SVG inside each engine (score ring `assessment.js:726`, sweep underline, v2 leaky-bucket `assessment-v2.js:56-89`). Doesn't scale to client work; style drifts per LM.

### What ships
`_engine/viz.js` exposing ~5 primitives, each taking data + reading existing brand tokens (`accent`/`font`/`ink` from the restyle) and returning branded SVG:
- `ring(value, max)` — score gauge (extracted from `assessment.js`)
- `bar(series)` — category / comparison bars
- `leakyBucket(amount, format)` — "$X leaking" visual (extracted from v2)
- `sparkline(points)` — repeat-taker trend (extracted from v2)
- `timeline(events)` — "operating record" evidence beat

### The move
Mostly **extraction + consolidation**, not net-new invention. Pull scattered inline SVG into one module, make each read brand tokens instead of hardcoded colors, repoint `assessment.js` / `assessment-v2.js` / `calculator.js` to call it. First real consumer is v2's `computed_outputs` (hence after Phase 2).

### Payoff at scale
A client's brand-mirrored LM renders charts in *their* accent/font automatically (primitives read the same tokens the restyle sets). One build, every client LM gets consistent on-brand viz.

### Anti-slop guardrail
Custom primitives only, no chart-library defaults. Motion stays subordinate (Phase 4 wires reveal).

### Testing
- Each primitive renders across 2-3 brand token sets.
- Visual parity: extracted ring / leaky-bucket match originals they replace.
- Smoke-test engines that now call `viz.js`.

## Phase 5 — brand-mirror from color to data (registrational personalization)

### What ships
Extend the existing query-param mechanism (threads `accent`/`font`/`logo`) to also thread prospect **data**: numbers, market, benchmarks. The engine reads them and:
- prefills `computed_outputs` inputs, and
- fills **templated prose slots** in `data.json`, so the LM restates the viewer's own numbers ("registrational" — the exemplar-research pillar for the built-for-me reaction).

For clients: their pipeline threads *their* prospect's data → the LM speaks each prospect's situation.

### Trust rule (same invariant as Phase 2)
Threaded params fill **inputs and prose slots only** — never formula source. Formulas stay in `data.json`, evaluated deterministically. Params are sanitized so nothing injects into the compute path. Keeps "operating record" honest even when personalized.

### Data flow
pipeline builds URL with brand + data params → engine substitutes into prose slots + prefills inputs → formulas still compute deterministically at view time.

### Testing
- Threaded data renders in prose slots + prefills inputs correctly.
- Injection test: malicious/garbage params cannot alter formula results.
- Parity: an LM with no data params behaves exactly as today.

## Phase 4 — motion / reveal layer in `shared.js`

### What ships
Wire NumberFlow (core web component, vanilla) + Motion vanilla API into `shared.js`. Three reveal helpers:
- number count-up on results,
- section-enter reveals,
- gradual metering of computed outputs (Periscopic "reveal the cost one beat at a time").

Motion fires **only on real numbers/evidence**, respects `prefers-reduced-motion`, opt-in per `data.json` so legacy LMs don't animate unexpectedly.

### Hard gate
`shared.js` loads on **all 57 live LMs** → cannot merge without **smoke-testing the 27 legacy assessments first**.

### Testing
- Reveal helpers fire on opt-in LMs, dormant on others.
- `prefers-reduced-motion` disables motion.
- All 27 legacy assessments render + function unchanged post-merge.
